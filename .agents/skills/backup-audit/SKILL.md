## Предназначение

Скилл для агента, проверяющего, что резервное копирование настроено
и реально работает. Выполняется по запросу пользователя; непроверенные
бэкапы равны их отсутствию. Выполнение самих операций
бэкапа/восстановления - скилл backup-restore.

## Порядок проверки

Работа ведется на сервере из корня рабочей копии (путь и подключение -
скилл production-diagnostics). Каждый шаг фиксирует результат;
замечания - пользователю с конкретными командами исправления.

### 1. Корректность настройки целей

В секции «Бэкапы» .env (схема - docs/deployment/backups.md):

- каждое имя из `BACKUP_DB_TARGETS` и `BACKUP_MEDIA_TARGETS` имеет
  запись `BACKUP_TARGET_<ИМЯ>` с известным префиксом (`mc:` / `rclone:`)
  и непустой спецификацией;
- имена целей - заглавные буквы, цифры, подчеркивание;
- списки непусты (пустой список = источник не копируется: осознанно
  ли это?);
- `MC_PATH` задан при наличии mc-целей; `BACKUP_DB_RETENTION_DAYS`
  задан (дефолт 14).

### 2. Свежесть и читаемость копий

```bash
bash scripts/backup.sh backup --verify
```

Проверяет каждую активную цель: дамп БД моложе 25 часов, читаемость
последнего дампа конвейером `mc cat`/`rclone cat | pg_restore -l`
(без выгрузки на диск), наличие содержимого `storage/` медиа-целей,
число объектов против источника (расхождение больше 5% - предупреждение).
Ошибки любого шага - деградация бэкапов, разбирать до закрытия аудита.

### 3. Расписание и логи

- расписание существует: `crontab -l` (строка scripts/cronjobs.sh,
  запуск `backup` в 23:01) либо `systemctl list-timers` (юнит
  personal-website-backup.timer); одновременно оба механизма не ведут;
- лог `${LOGS_ROOT}/backup.log` (cron) или `journalctl -u
  personal-website-backup.service` (timer): запуски происходят по
  расписанию, ошибок и пропусков нет;

```bash
grep -c "Резервное копирование" ${LOGS_ROOT}/backup.log
tail -n 200 ${LOGS_ROOT}/backup.log | grep -iE "error|exception|traceback"
```

### 4. Место и ретеншн

- локальные дампы `${BACKUP_ROOT}/db/`: старше
  `BACKUP_DB_RETENTION_DAYS` дней отсутствуют, рост каталога ограничен;
- цели: число дампов в `db/` каждой цели соответствует ретеншну
  (устаревшие удаляются автоматически при каждом бэкапе БД);

```bash
ls -lt ${BACKUP_ROOT}/db/ | head
du -sh ${BACKUP_ROOT}/db
```

- сравнить занятое место целей с объемом медиа-хранилища: расхождение
  кратно больше ожидаемого - признак накопления мусора или отказа
  зеркальной синхронизации.

### 5. Правило 3-2-1

Минимум две цели, одна - offsite (не тот же сервер). Для домашнего
сервера offsite-цель обязательна. У offsite-цели - учетные данные,
независимые от приложения; у S3-цели - отдельный пользователь
с минимальными правами.

## Учебное восстановление (restore-дрилл)

Учебное восстановление на тестовом окружении (personal-website-test;
прод не трогать) - когда пользователь сочтет нужным. Порядок - скилл
backup-restore, сверка после каждого шага:

1. развернуть стек тестового окружения (скилл server-setup);
2. восстановить медиа из цели: `restore_media <цель>` - число объектов
   и суммарный размер совпадают с источником (допуск - служебные файлы
   ОС, например .DS_Store);
3. восстановить БД из цели: `restore_db <цель>` - счетчики ключевых
   таблиц и django_migrations совпадают с источником, `/health/` - 200;
4. учебный прогон смены типа хранилища туда-обратно через временную
   цель (docs/deployment/backups.md, раздел 7): filesystem -> S3-бакет
   -> обратно; после каждого переноса сверять число объектов и размеры;
5. итоги дрилла: что проверено, найденные дефекты, время выполнения;
   дефекты кода оформляются отдельными issue/PR.

## Ограничения

- Аудит не изменяет данные целей: только чтение, листинг и verify
  (verify новых дампов не создает).
- Деструктивные операции (удаление старых дампов вручную, перезапуск
  сервисов) - только с явного разрешения пользователя.
