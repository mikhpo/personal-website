## Предназначение

Скилл для агента, проверяющего, что резервное копирование настроено и реально работает. Выполняется по запросу пользователя; непроверенные бэкапы равны их отсутствию. Выполнение самих операций бэкапа/восстановления - скилл backup-restore; учебное восстановление на тестовом окружении - скилл restore-drill (только по явному запросу пользователя).

## Порядок проверки

Работа ведется на сервере из корня рабочей копии (путь и подключение - скилл production-diagnostics). Каждый шаг фиксирует результат; замечания - пользователю с конкретными командами исправления.

### 1. Корректность настройки целей

В секции «Бэкапы» .env (схема - [docs/deployment/backups.md](../../../docs/deployment/backups.md)):

- каждое имя из `BACKUP_DB_TARGETS` и `BACKUP_MEDIA_TARGETS` имеет запись `BACKUP_TARGET_<ИМЯ>` с известным префиксом (`mc:` / `rclone:`) и непустой спецификацией;
- имена целей - заглавные буквы, цифры, подчеркивание;
- списки целей непусты; пустой список означает, что источник не копируется ни в одну цель - сообщить пользователю и выяснить, осознанно ли это;
- `MC_PATH` задан при наличии mc-целей; `BACKUP_DB_RETENTION_DAYS` задан (дефолт 14).

### 2. Свежесть и читаемость копий

```bash
bash scripts/backup.sh backup --verify
```

Проверяет каждую активную цель: дамп БД моложе 25 часов, читаемость последнего дампа конвейером `mc cat`/`rclone cat | pg_restore -l` (без выгрузки на диск), наличие содержимого `storage/` медиа-целей, сверка числа объектов цели с источником. Зеркало полное: любое расхождение - предупреждение в журнале. Ошибки любого шага - деградация бэкапов, разбирать до закрытия аудита.

### 3. Расписание и логи

- расписание существует: `crontab -l` (строка scripts/cronjobs.sh, запуск `backup` в 23:01 МСК) либо `systemctl list-timers` (юнит personal-website-backup.timer); одновременно оба механизма не ведут;
- лог `${LOGS_ROOT}/backup.log` (cron) или `journalctl -u personal-website-backup.service` (timer): запуски происходят по расписанию, ошибок и пропусков нет;

```bash
grep -c "Резервное копирование" ${LOGS_ROOT}/backup.log
tail -n 200 ${LOGS_ROOT}/backup.log | grep -iE "error|exception|traceback"
```

### 4. Место и ретеншн

- локальные дампы `${BACKUP_ROOT}/db/`: старше `BACKUP_DB_RETENTION_DAYS` дней отсутствуют, рост каталога ограничен;
- цели: число дампов в `db/` каждой цели соответствует ретеншну (устаревшие удаляются автоматически при каждом бэкапе БД);

```bash
ls -lt ${BACKUP_ROOT}/db/ | head
du -sh ${BACKUP_ROOT}/db
```

- сравнить занятое место цели с объемом медиа-хранилища: зеркало полное, поэтому заметная разница размеров - признак незавершенной синхронизации или посторонних файлов в цели.

### 5. Вторая копия и offsite-цель

Три копии данных (оригинал и две цели), два разных места хранения, одна копия вне сервера; детали - [docs/deployment/backups.md](../../../docs/deployment/backups.md), раздел 8. Обязательное требование - хотя бы одна offsite-цель (не тот же сервер); число целей сверх этого - рекомендация. У offsite-цели - учетные данные, независимые от приложения; у S3-цели - отдельный пользователь с минимальными правами.

## Ограничения

- Аудит не изменяет данные целей: только чтение, листинг и verify (verify новых дампов не создает).
- Деструктивные операции (удаление старых дампов вручную, перезапуск сервисов) - только с явного разрешения пользователя.
