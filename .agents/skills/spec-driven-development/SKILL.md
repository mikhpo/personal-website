## Предназначение

Скилл фиксирует методику поэтапных локальных планов для крупных целей (milestone из множества задач): план создается один раз, а затем разные агенты поочередно выполняют этапы, каждый - полным циклом ветка-PR-merge. Методика решает две задачи: продолжение работы другим агентом или в другой сессии с места остановки и защиту от потери контекста из-за превышения лимита или технического сбоя.

Применяется: при планировании новой крупной цели (создание плана) и при обнаружении в репозитории плана этой методики - каталога с файлами spec.md, plan.md, tasks.md, guide.md (работа по плану).

## Создание плана

### Хранение

Планы хранятся локально, вне git: каталог выбирается из уже игнорируемых в `.gitignore` - под конкретную цель и время; заранее фиксированного места нет. Выбранный каталог указывается в TODO.md и памяти Claude, чтобы план нашли следующие сессии.

### Четыре файла плана

- spec.md - требования: подробно, полностью отражает все озвученные требования пользователя из исходной задачи и уточнений диалога; зафиксированные решения («решение пользователя») и ограничения, чтобы следующие агенты не пересматривали их вслепую.
- plan.md - план: детальный, без недоговорок и «...»; каждый этап с деталями реализации (файлы, правки, семантика), точными командами проверки и критериями завершения.
- tasks.md - чеклист: рубежи каждого этапа (ветка создана, изменения внесены, PR открыт, CI, merge, закрытие задач и далее) со статусами; текущее состояние (какой этап, какой рубеж); журнал событий с датами.
- guide.md - инструкция для агентов о том, как работать по плану: точка входа, цикл этапа, правила фиксации прогресса, запреты.

### Разбивка на этапы

- Детальный план разбивается на несколько этапов - по количеству PR: один этап = один PR.
- Число PR уменьшается группировкой: связанные задачи с общими файлами закрываются одним PR (2-4 задачи на PR нормально).
- Кроме кодовых этапов (PR) возможны операционные (анализ, работа на сервере, миграция) - без PR, со своими шагами и рубежами.
- Каждый этап связывается с задачами трекера платформы хостинга (milestone/issue), которые он закрывает; в описании PR даются ссылки на задачи этапа.
- Этапы самодостаточны: агенту для работы нужны только guide.md, tasks.md, spec.md и раздел своего этапа в plan.md - без истории сессий.
- Зависимости этапов указываются явно.

### Проверка плана после создания

- git status не показывает каталог плана (хранилище игнорируется).
- npx markdownlint-cli по всем файлам плана - без замечаний.
- Симуляция: достаточно ли чтения guide -> tasks -> spec -> этап plan для старта первого этапа без контекста создателя.
- Указатели: TODO.md и память Claude ссылаются на план (иначе следующая сессия его не найдет).

## Работа по плану

### Точка входа агента

1. Прочитать guide.md - протокол работы.
2. Прочитать tasks.md - текущий этап и рубеж (первый неотмеченный чекбокс).
3. Прочитать spec.md (решения не пересматривать) и раздел своего этапа в plan.md.
4. Продолжить с текущего рубежа; при расхождении состояния (сбой, другая сессия) свериться с журналом tasks.md, `git branch -a` и списками PR/задач на платформе хостинга.

### Цикл кодового этапа (этап = PR)

Работа с PR, CI и задачами ведется средствами платформы хостинга репозитория; конкретные команды и скиллы указываются в guide.md плана под текущую платформу - методика от платформы не зависит.

1. Создать ветку этапа (имя указано в плане, формат `feat/<номер первой задачи>-<слаг>`).
2. Внести изменения по списку файлов этапа.
3. Прогнать тесты: `poetry run pytest` и `npm test` - обязательно перед каждым коммитом независимо от затронутых файлов (правило CLAUDE.md); дополнительные проверки этапа (интеграционные, линтеры, прогоны скриптов) - по списку в плане.
4. Обновить CHANGELOG.md (скилл update-changelog), закоммитить (формат CLAUDE.md, без Co-Authored-By), убедиться, что pre-commit прошел.
5. Запушить ветку и создать PR (скилл pr-description; в описании - ссылки на задачи этапа).
6. Дождаться окончания CI (зеленые checks PR на платформе хостинга) и подтверждения пользователя.
7. Влить изменения (merge - только после явного подтверждения пользователя; общий план и зеленый CI его не заменяют).
8. Закрыть связанные задачи этапа на платформе хостинга.
9. Закрыть ветку (`git push origin --delete <ветка>`).
10. Зафиксировать промежуточные результаты выполнения плана: отметить чекбоксы этапа, сменить статус на done, записать в журнал tasks.md итог этапа (PR, дата, замечания).
11. Следующий этап повторяет цикл - другим агентом или в другой сессии.

### Правила фиксации прогресса (защита от потери контекста)

- tasks.md обновляется точечно после каждого рубежа цикла, а не в конце этапа: именно это позволяет новому агенту подхватить план с точного места остановки после лимита контекста или сбоя.
- Статусы этапов: pending / in_progress / in_review / done / blocked; done - только после merge + закрытия задач + удаления ветки; blocked - с причиной в журнале.
- Отклонения от плана фиксируются записью в журнал (что, почему, чем заменено); plan.md и spec.md не переписывать без решения пользователя.
- Записи в журнал датировать (ГГГГ-ММ-ДД).

### Запреты

- Не пушить в main; только ветки и PR.
- Не мержить без явного подтверждения пользователя.
- Не коммитить код с падающими тестами или линтерами.
- Не выполнять этапы вне очереди (план последовательный; параллельность - только с явного указания пользователя).
- Продакшен-операции (операционные этапы) - каждый рубеж с явным подтверждением пользователя.
