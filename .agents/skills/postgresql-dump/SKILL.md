## Предназначение

Создание переносимого логического дампа БД стандартной утилитой pg_dump для разовых операций: копия перед изменениями, перенос между кластерами, автономная резервная копия. Регулярные дампы по расписанию выполняет система бэкапов проекта (`bash scripts/backup.sh backup_db`, скилл backup-restore) - они же годятся как источник для разовых операций.

## Совместимость версий

Версия pg_dump обязана быть не ниже версии сервера (кластера). Проверить:

```bash
pg_dump --version                       # версия клиента
psql … -c "SELECT version();"           # версия сервера
```

Если доступный по умолчанию клиент младше сервера, выбрать совместимый: установить пакет нужной версии либо вызвать нужный бинарник явным путём. В системах с несколькими установленными версиями ориентироваться на вывод `--version`, а не на расположение файла.

## Параметры подключения и аутентификация

Параметры те же, что использует приложение (см. [docs/deployment/database.md](../../../docs/deployment/database.md), раздел 1). Утилиты libpq принимают их флагами:

* `-h <хост>` - имя хоста или путь к каталогу unix-сокета;
* `-p <порт>` - порт сервера;
* `-U <пользователь>` - имя пользователя БД;
* `-d <база>` - имя базы данных.

Пароль - через переменную окружения `PGPASSWORD` либо файл `~/.pgpass`.

## Соглашение об имени файла

`<база>_<дата>_<время>.dump`, где дата в формате ISO (`YYYY-MM-DD`), время - МСК в формате `HHMM`. Суффикс даты и времени обеспечивает лексикографическую сортировку от старых к новым. Пример: `personal_website_2026-08-25_1657.dump`.

Регулярные дампы системы бэкапов пишутся в `${BACKUP_ROOT}/db/` и копируются в `db/` каждой настроенной цели (см. [docs/deployment/backups.md](../../../docs/deployment/backups.md)); для разовых операций соглашение то же.

## Назначение флагов

* `-Fc` - custom-формат: компактный, допускает выборочное восстановление и параллельную работу.
* `--no-privileges` - пропустить `GRANT`/`REVOKE`: роли и права источника обычно отсутствуют на целевом кластере.
* `--no-subscriptions` / `--no-publications` - исключить логическую репликацию (не относится к приложению, избегает шума при восстановлении на другом кластере).

## Создание дампа

Разовый дамп можно выполнить двумя способами: скриптом-помощником (удобнее для агента - сам выбирает совместимую версию клиента и сообщает результат в JSON) или прямой командой pg_dump.

### Скрипт-помощник

`scripts/pg-dump.sh` - неинтерактивный wrapper над pg_dump (без выгрузки во внешнее хранилище). Параметры подключения - флагами или переменными окружения libpq (`PGHOST`, `PGPORT`, `PGUSER`, `PGDATABASE`, `PGPASSWORD`), пароль через `PGPASSWORD` или `~/.pgpass`.

```bash
PGPASSWORD='<пароль>' bash scripts/pg-dump.sh \
    --host <хост> --port <порт> --user <пользователь> --dbname <база>
```

Особенности:

* имя файла по умолчанию `<база>_<дата>.dump` (переопределяется `--output`);
* при существующем файле завершается с кодом 4, перезапись - `--force`;
* результат (путь, база, размер) - одной строкой в stdout, диагностика - в stderr;
* коды возврата: `0` успех, `2` аргументы, `3` ошибка pg_dump, `4` файл существует;
* версию pg_dump (не ниже версии сервера) обеспечивает вызывающая сторона.

### Прямая команда

```bash
export PGPASSWORD='<пароль>'
pg_dump -h <хост> -p <порт> -U <пользователь> -d <база> \
    -Fc --no-privileges --no-subscriptions --no-publications \
    -f personal_website_$(date +%F_%H%M).dump
```

## Проверка дампа

```bash
pg_restore -l personal_website_*.dump | head    # состав и размер
```

## Рекомендации

* Снимать дамп при остановленном приложении или в окно минимальной записи для консистентной копии.
* Если кластер требует SSL, использовать параметры подключения приложения ([docs/deployment/database.md](../../../docs/deployment/database.md)).
* Восстановление дампа - см. скилл postgresql-restore; восстановление из целей бэкапов - скилл backup-restore (`scripts/backup.sh restore_db`).
