## Предназначение

Скилл для агента, выполняющего операции резервного копирования
и восстановления на сервере: регулярные и разовые бэкапы, восстановление
БД и медиа, перенос медиа между типами хранилища. Проверка того, что
бэкапирование настроено и реально работает, - отдельный скилл
backup-audit.

## Вход и команды

Все операции - через хостовой вход `scripts/backup.sh` (из корня рабочей
копии на сервере); скрипт читает .env и диспетчеризует по DEPLOY_MODE
(compose - контейнер application, systemd - venv на хосте). Работа
неинтерактивна.

```bash
bash scripts/backup.sh backup              # БД + медиа в настроенные цели
bash scripts/backup.sh backup --verify     # проверка целей без нового бэкапа
bash scripts/backup.sh backup_db           # только БД (дамп + цели + ретеншн)
bash scripts/backup.sh backup_media        # только медиа (зеркальная синхронизация)
bash scripts/backup.sh restore_db <источник> [--dump <имя>]
bash scripts/backup.sh restore_media <цель>
```

`restore_db` принимает имя цели (берется последний дамп `db/` цели, либо
конкретный - флагом `--dump`) или путь к файлу дампа на диске. Лог
операций - журнал Django (логгер backup).

## Источники, цели, переменные

Источники и списки целей задаются в секции «Бэкапы» .env:

- `BACKUP_DB_TARGETS`, `BACKUP_MEDIA_TARGETS` - имена целей через пробел
  (пустой список - источник не копируется);
- каждая цель - запись `BACKUP_TARGET_<ИМЯ>='<префикс>:<спецификация>'`:
  `mc:alias/бакет[/префикс]` (S3/MinIO через MinIO Client) или
  `rclone:remote:путь` / локальный путь (диски, облачные хранилища);
- `MC_PATH` - путь к mc (только для mc-целей);
- `BACKUP_DB_RETENTION_DAYS` - срок хранения дампов.

Полная схема целей, семантика зеркала и расписание -
docs/deployment/backups.md.

Инструменты целей настраиваются на сервере единовременно:

```bash
mc alias set <алиас> <endpoint> <access-key> <secret-key>
rclone config    # remote для облачных целей; локальным путям remote не нужен
```

Доступ rclone к медиа-бакету при STORAGE_TYPE=s3 отдельной настройки
не требует (remote собирается из RCLONE_CONFIG_* процесса).

## Восстановление

Порядок обязателен: сначала хранилище, потом БД. Обоснование: миграция
gallery/0013 читает файлы через хранилище - восстановление с нуля
(пустая БД + миграции) требует доступности медиа до migrate.

1. `bash scripts/backup.sh restore_media <цель>` - недеструктивное
   копирование из `storage/` цели;
2. `bash scripts/backup.sh restore_db <цель | путь>` - восстановление
   с `--clean --if-exists` (объекты пересоздаются); конкретный дамп -
   `--dump <имя>`;
3. проверка целостности: счетчики таблиц и примененные миграции -
   скилл postgresql-restore; живость - `curl http://127.0.0.1:${DJANGO_PORT}/health/`.

Восстановление на новом сервере - до переключения DNS. Разовые операции
с внешними дампами вне целей бэкапа (pg_dump/pg_restore напрямую,
два варианта восстановления) - скиллы postgresql-dump, postgresql-restore.

## Перенос медиа при смене типа хранилища

Отдельного механизма переноса нет: используется временная цель
`BACKUP_TARGET_<ИМЯ>` (добавить в .env, включить в
`BACKUP_MEDIA_TARGETS`, `backup_media`, переключить `STORAGE_TYPE`
и параметры хранилища, перезапустить приложение, `restore_media`,
сверить число объектов, удалить временную цель). Пошагово -
docs/deployment/backups.md, раздел 7.

## Ограничения

- Зеркальная синхронизация медиа деструктивна для целей: объекты,
  исчезнувшие из источника, удаляются из целей (целевое поведение);
  защита от случайного удаления - лента дампов БД.
- Не запускать восстановление в рабочей БД без свежей точки отката
  (дамп источника) и явного разрешения пользователя.
- Пароли и подтверждения не запрашиваются: все учетные данные - в .env
  и настроенных алиасах/remotes сервера.
