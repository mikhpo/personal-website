## Предназначение

Проверять тексты репозитория и исправлять нарушения при правке документации, комментариев или докстрингов, а также перед Pull Request. Область: docs/, README.md, docs/CONTRIBUTING.md, .env.example, CHANGELOG.md, диаграммы docs/diagrams/, комментарии и докстринги исходного кода (backend/, scripts/, frontend/).

## Правила содержания

- Документировать только актуальное состояние: без истории выбора, пост-мортемов, разделов «осознанно не поддерживается», рассуждений об ограничениях и vendor-lock; история - в коммитах и CHANGELOG
- Не фиксировать изменчивые статусы: какой сценарий действующий прод, какое целевое состояние, чем и где что проверяется, какая система CI основная - это меняется независимо от документации
- Различать требования и рекомендации явно: писать, что именно обязательно, а что - выбор администратора на текущем этапе
- Не ограничивать без необходимости: если возможны варианты (например, разработка с filesystem или S3), не утверждать единственный
- Формулировки о внешних системах осторожные: «у части провайдеров может отличаться», а не универсальные утверждения истины; конкретное значение приводить как пример, не как правило
- Упомянутый механизм или скрипт документировать с примером: например, подстановка envsubst с командой, вызов скрипта с явным аргументом

## Правила комментариев в коде

- Комментарий оправдан, только когда добавляет неочевидное: причину нетривиального решения, внешнее ограничение, неявный контекст; комментарии, отвечающие на вопрос «что делает код», вырезать - код говорит это сам
- Без комментариев о предыдущем или удаленном поведении («больше не настраивается, потому что...»): история - в git; при удалении кода удалять его комментарии целиком
- Только актуальное состояние - и в комментариях: без упоминаний прошедших состояний и причин недавних замен
- Русский язык; термины и типографика - те же правила, что для документации: простые выражения вместо жаргона, дефис вместо длинного тире, «->» вместо стрелки
- Глаголы в неопределенной форме: «# выйти в случае ошибки», а не «# выйдите»

## Правила докстрингов

- Докстринги обязательны для публичных классов и функций, конвенция PEP 257, русский язык
- Структура: краткое назначение, при необходимости детали поведения и секции Args/Returns/Raises (образец - backend/backup/)
- Докстринг отвечает «зачем» и о неочевидном поведении; пересказ сигнатуры и типов (есть в аннотациях) не нужен

## Правила стиля

- docs/ - связная проза для людей: полные предложения, объяснения «почему» и «что из этого следует»; рубленый телеграфный стиль - только в скиллах, списках команд и CHANGELOG
- Глаголы в неопределенной форме, не в повелительном наклонении («удалить», а не «удалите»)
- Простые выражения вместо жаргона: «прокси-сервер с HTTPS», а не «слой терминирования HTTPS»; без «живость», «vhost», «de facto», «монты» - термины, непривычные читателю, заменять говорящими
- Типографика: без жирного шрифта, дефис вместо длинного тире, «->» вместо стрелки
- Без разделов «Содержание:» - навигация по заголовкам Markdown

## Размещение по файлам

- README.md: минимальные указания на развертывание обязательны (setup.sh, deploy.sh, ссылка на матрицу); детальные разделы CI/CD и порядок работы с Taskfile - в docs/CONTRIBUTING.md
- .env.example: только назначение переменной и ссылка на документ; без описания вариантов размещений сервисов
- CHANGELOG.md: пункт - одна фраза, без деталей реализации, в стиле существующих записей (см. скилл update-changelog)
- Диаграммы .puml: обобщенная картина, а не перечисление всех вариантов; System_Ext не больше 3 параметров; лаконичные описания контейнеров; без note и ссылок на документацию

## Ссылки

- Упоминание markdown-файла репозитория в прозе - кликабельный markdown-URL с корректным относительным путем
- Исключения: YAML frontmatter, заголовки, имена файлов внутри команд в код-спанах

## Проверки после правки

- `npm run markdownlint` - все markdown-файлы репозитория
- `task render-diagrams` - при правке файлов .puml
- `poetry run ruff check . --fix` и `poetry run mypy .` - при правке комментариев и докстрингов в коде
