# Резервное копирование

Конфигурация бэкапов выбирается независимо от остальных параметров
развертывания (способ запуска приложения, база данных, хранилище,
прокси). Система реализована Django-приложением `backend/backup/`
с management-командами; хостовой вход -
[scripts/backup.sh](../../scripts/backup.sh), диспетчеризующий
по DEPLOY_MODE: compose - исполнение в контейнере application,
systemd - интерпретатор виртуального окружения на хосте. Работа
полностью неинтерактивна: без паролей и подтверждений, поэтому годится
для cron и systemd timer.

## 1. Источники и селективность

У системы два независимых источника, и каждому назначается свой список
целей (переменные .env):

- `BACKUP_DB_TARGETS` - имена целей дампов БД через пробел; пусто - БД
  не копируется;
- `BACKUP_MEDIA_TARGETS` - имена целей медиафайлов; пусто - медиа
  не копируются.

Списки независимы: БД и медиа могут отправляться в разные места.
Например, `BACKUP_DB_TARGETS="LOCALDISK OFFSITE"`
и `BACKUP_MEDIA_TARGETS="OFFSITE"`.

Значения списков - не фиксированный перечень, а произвольные имена
целей, которые администратор выбирает сам. От имени требуется три
условия: имена разделяются пробелами; имя состоит из заглавных букв,
цифр и подчеркивания (`^[A-Z_][A-Z0-9_]*$`); для каждого имени
в .env определена запись `BACKUP_TARGET_<ИМЯ>` с известным префиксом
и непустой спецификацией (раздел 2). Нарушение любого условия
завершает команду ошибкой с указанием причины; единственный
«специальный» вариант значения - пустая строка, отключающая копирование
источника (в режиме `--verify` она считается ошибкой настройки).

Источник читается напрямую, без промежуточной копии на диск. База
данных снимается дампом `pg_dump -Fc` в локальный каталог
`${BACKUP_ROOT}/db/` с проверкой читаемости `pg_restore -l`; клиент
PostgreSQL уже входит в образ приложения (compose) или устанавливается
на хост (systemd). Медиа копируются из хранилища напрямую: каталог
`${STORAGE_ROOT}` при `STORAGE_TYPE=filesystem`, медиа-бакет при
`STORAGE_TYPE=s3` (mc адресует его алиасом `MINIO_ALIAS`, rclone -
remote `media`, собираемым из переменных `RCLONE_CONFIG_*`; rclone.conf
для доступа к медиа-бакету не нужен).

## 2. Цели и их настройка

Цель - именованная запись в .env:

```text
BACKUP_TARGET_<ИМЯ>='<префикс>:<спецификация>'
```

Имя состоит из заглавных букв, цифр и подчеркивания
(`^[A-Z_][A-Z0-9_]*$`). Префикс выбирает инструмент копирования:

| Префикс | Спецификация | Инструмент |
| --- | --- | --- |
| `mc:` | `alias/бакет[/префикс]` | MinIO Client - S3/MinIO-цели |
| `rclone:` | `remote:путь` или локальный путь | rclone - диски и облачные хранилища |

Примеры:

```text
BACKUP_TARGET_OFFSITE='mc:local/backups'
BACKUP_TARGET_LOCALDISK='rclone:/mnt/backup'
BACKUP_TARGET_YADISK='rclone:yadisk:site-backup'
```

Раскладка внутри цели одинакова для обоих префиксов: дампы БД лежат
в `db/`, медиа - в `storage/`.

Новый механизм копирования добавляется плагином: подкласс `Target`
в [backend/backup/targets.py](../../backend/backup/targets.py) и запись
в реестре `TARGET_PREFIXES`; команды и оркестрация не меняются.

Инструменты настраиваются на сервере один раз:

```bash
# mc: алиас для S3-целей (совпадает с MINIO_ALIAS для медиа-бакета
# или отдельный алиас для целей бэкапов)
mc alias set <алиас> <endpoint> <access-key> <secret-key>

# rclone: remote для облачных целей (Яндекс Диск, Google Drive, SFTP);
# локальные диски remote не требуют - указывается абсолютный путь
rclone config
```

В Docker Compose команды резервного копирования выполняются внутри
контейнера application, поэтому алиасы нужны контейнерному клиенту mc.
Алиас медиа-хранилища `MINIO_ALIAS` настраивается entrypoint.sh при
каждом старте контейнера из переменных `MINIO_SERVER_URL`,
`MINIO_ACCESS_KEY` и `MINIO_SECRET_KEY`. Дополнительные mc-алиасы
(цели на других серверах S3) настраиваются вручную: в systemd-режиме -
один раз на хосте, в compose - в контейнере application, повторяя
настройку после пересоздания контейнера. Поэтому для mc-целей в
compose-режиме удобно использовать тот же алиас `MINIO_ALIAS`.

Переменные окружения (секция «Бэкапы» .env):

- `BACKUP_DB_TARGETS`, `BACKUP_MEDIA_TARGETS` - списки целей;
- `MC_PATH` - путь к mc (только при наличии mc-целей);
- `BACKUP_DB_RETENTION_DAYS` - срок хранения дампов.

Шифрование бэкапов не используется (решение пользователя): инструменты
с обязательным шифрованием (restic) не подходят, файлы в целях остаются
обыными и читаются штатными средствами.

## 3. Семантика копирования

Медиа копируются зеркальной синхронизацией (`mc mirror --overwrite
--remove` / `rclone sync`): объекты, исчезнувшие из хранилища,
удаляются из целей, поэтому orphan-объектов в целях не накапливается -
это целевое поведение. Принятое следствие: зеркало не защищает медиа
от случайного удаления, а дампы БД медиа не содержат. Версионирование
бакета осознанно не включается: noncurrent-версии тарифицируются
на managed S3 без верхней границы, а медиафайлы пере-загружаемы из
архива владельца.

База данных копируется датированными дампами
`<база>_<дата>_<время>.dump` (UTC, например
`personal_website_2026-08-25_1357.dump`): они раскладываются в `db/`
каждой цели списка, и новые дампы не затирают предыдущие.

Ретеншн управляет хранением: дампы старше `BACKUP_DB_RETENTION_DAYS`
дней удаляются из целей и из локального `${BACKUP_ROOT}/db` при каждом
бэкапе БД.

## 4. Команды

Все команды выполняются через хостовой вход - из корня рабочей копии
на сервере:

```bash
bash scripts/backup.sh backup              # БД + медиа в настроенные цели
bash scripts/backup.sh backup --verify     # проверка целей без нового бэкапа
bash scripts/backup.sh backup_db           # только БД
bash scripts/backup.sh backup_media        # только медиа
bash scripts/backup.sh restore_db OFFSITE              # БД из последнего дампа цели
bash scripts/backup.sh restore_db /path/to/file.dump   # БД из локального файла
bash scripts/backup.sh restore_media OFFSITE           # медиа из storage/ цели
```

Проверка `--verify` проходит по каждой активной цели. Для БД она
проверяет наличие дампа моложе 25 часов и читаемость последнего дампа
`pg_restore -l` конвейером (`mc cat` / `rclone cat` -> `pg_restore`)
без выгрузки на диск. Для медиа - наличие содержимого `storage/`
и сверку числа объектов с источником: зеркало полное, любое
расхождение попадает в журнал как предупреждение.

Непроверенные бэкапы равны их отсутствию: `--verify` предназначен
для аудита (скилл backup-audit). Учебное восстановление на тестовом
окружении выполняет отдельный скилл restore-drill.

## 5. Расписание: cron и systemd timer

Основной механизм - cron хоста через
[scripts/cronjobs.sh](../../scripts/cronjobs.sh) (добавляется
установщиками): ежедневный запуск `backup` в 23:01 МСК, вывод - в
`${LOGS_ROOT}/backup.log`. Время в crontab интерпретируется в системной
таймзоне хоста - установщики фиксируют ее значением Europe/Moscow
(scripts/server/setup.sh, scripts/docker/setup.sh). Добавление
идемпотентно: повторный запуск не дублирует задачу в crontab.

Альтернатива - systemd timer: он догоняет пропущенные при выключенном
сервере запуски и пишет логи в journal. Механизмы равноправны,
в scripts/ дублируется только cron. Юниты создаются вручную.
Время OnCalendar, как и у cron, задается в системной таймзоне хоста.

`/etc/systemd/system/personal-website-backup.service`:

```ini
[Unit]
Description=personal-website backup (db + media)

[Service]
Type=oneshot
User=<пользователь>
WorkingDirectory=/srv/personal-website
ExecStart=/bin/bash scripts/backup.sh backup
```

`/etc/systemd/system/personal-website-backup.timer`:

```ini
[Unit]
Description=Ежедневный запуск резервного копирования

[Timer]
OnCalendar=*-*-* 23:01:00
Persistent=true

[Install]
WantedBy=timers.target
```

Включение и проверка:

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now personal-website-backup.timer
systemctl list-timers personal-website-backup.timer
journalctl -u personal-website-backup.service --since today
```

При переходе с cron на timer удалить задачу из crontab (`crontab -e`),
чтобы копирование не выполнялось дважды.

## 6. Восстановление

При восстановлении с нуля (пустая база плюс миграции) медиа должны
быть доступны до запуска миграций: миграция `gallery/0013` читает
файлы через хранилище. В таком сценарии восстанавливать сначала
хранилище, потом базу.

1. Медиа: `bash scripts/backup.sh restore_media <ИМЯ>` - недеструктивное
   копирование из `storage/` цели (файлы хранилища, отсутствующие
   в цели, не удаляются).
2. База: `bash scripts/backup.sh restore_db <ИМЯ>` - последний дамп
   цели конвейером в `pg_restore` (`--clean --if-exists`, объекты
   пересоздаются), либо `restore_db <путь>` для файла на диске;
   конкретный дамп цели выбирается флагом `--dump <имя>`.
3. Целостность проверяется счетчиками таблиц и примененными
   миграциями (скилл postgresql-restore).

Восстановление на новом сервере выполняется до переключения DNS;
работоспособность после восстановления подтверждается эндпоинтом
`/health/`.

## 7. Смена типа хранилища

Перенос медиа между бэкендами (filesystem <-> S3) выполняется командами
бэкапов: старое хранилище служит источником, новое - приемником,
а мостом между ними выступают постоянные цели бэкапов. Медиа-бакет
в S3-режиме хранит медиа в префиксе `media/`, поэтому цели получают
чистую медиатеку без статики.

1. На старом хранилище выполнить `bash scripts/backup.sh backup_media` -
   текущее хранилище зеркально синхронизируется в настроенные цели
   (`BACKUP_MEDIA_TARGETS`).
2. Изменить `STORAGE_TYPE` и параметры хранилища в .env и перезапустить
   приложение - хранилище теперь новое и пустое.
3. Выполнить `bash scripts/backup.sh restore_media <ИМЯ>` - медиа из
   выбранной цели копируются в новое хранилище.
4. Проверить число объектов (`backup_media --verify`) и работать
   с настроенными целями дальше: переконфигурация целей не требуется.

Для перехода в обратную сторону процедура повторяется в обратном
порядке с теми же целями.

## 8. Правило 3-2-1 и защита целей

Правило 3-2-1: три копии данных (оригинал и две цели бэкапа), два
разных места хранения, одна копия вне сервера (offsite).

Техническое ограничение одно: хотя бы одна цель должна быть offsite,
то есть не на том же сервере, - «бэкап на другом диске того же
сервера» offsite не считается. Число целей сверх этого - рекомендация
по правилу 3-2-1, а не техническое требование: сколько целей вести
на каждом этапе развития проекта, решает администратор. У offsite-цели -
учетные данные, независимые от приложения: компрометация хоста не
должна уничтожать доступные на запись цели. Для S3-цели заводится
отдельный пользователь с минимальными правами на бакет бэкапов.

Критичные для восстановления данные - только датированные дампы БД
в целях: оригиналы медиа пере-загружаемы из архива владельца,
а сертификаты прокси выпускаются и продлеваются certbot
автоматически ([proxy.md](./proxy.md)).

## 9. Оповещения о результатах

Каждый реальный запуск команд backup, backup_db и backup_media
сопровождается письмом-отчетом на адрес BACKUP_NOTIFY_EMAIL; проверка
целей (--verify) уведомлений не создает. Восстановление (restore_*)
отчетами не покрывается: это редкие ручные операции, результат виден
оператору сразу.

Отчет содержит имя команды, хост, время начала (UTC) и длительность.
При успехе в отчет входят разделы «База данных» (цели, имя и объем
дампа, ретеншн) и «Медиа» (цели, число объектов и объем хранилища) -
только по тому, что делала команда. При ошибке разделов нет: письмо
содержит полный журнал команды. Запуск с ненастроенными целями письмом
не сопровождается: бэкапирование не выполнялось.

Отправка выполняется штатным django send_mail от адреса
DEFAULT_FROM_EMAIL. Пустое значение BACKUP_NOTIFY_EMAIL отключает
оповещения. Отказ почтового сервера не меняет код возврата команды -
в журнал пишется предупреждение, бэкап считается выполненным. Первый
реальный прогон с доставкой письма проверяется на продакшен-сервере
письмом через django shell.
