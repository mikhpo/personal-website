# Резервное копирование

Конфигурация бэкапов выбирается независимо от остальных параметров
развертывания (способ запуска приложения, база данных, хранилище, прокси).
Система реализована Django-приложением `backend/backup/` с
management-командами; хостовой вход - [scripts/backup.sh](../../scripts/backup.sh),
диспетчеризующий по DEPLOY_MODE: compose - исполнение в контейнере
application, systemd - интерпретатор виртуального окружения на хосте.
Работа полностью неинтерактивна: без паролей и подтверждений, пригодна
для cron/systemd timer.

Содержание:

1. Источники и селективность
2. Цели и их настройка
3. Семантика копирования
4. Команды
5. Расписание: cron и systemd timer
6. Восстановление
7. Смена типа хранилища
8. Правило 3-2-1 и защита целей

## 1. Источники и селективность

Два независимых источника, каждому - свой список целей (переменные .env):

- `BACKUP_DB_TARGETS` - имена целей дампов БД через пробел; пусто - БД
  не копируется;
- `BACKUP_MEDIA_TARGETS` - имена целей медиафайлов; пусто - медиа
  не копируются.

Списки независимы: БД и медиа могут отправляться в разные места. Пример:
`BACKUP_DB_TARGETS="LOCALDISK OFFSITE"`, `BACKUP_MEDIA_TARGETS="OFFSITE"`.

Способ чтения источника:

- БД - дамп `pg_dump -Fc` в локальный каталог `${BACKUP_ROOT}/db/`
  с проверкой читаемости `pg_restore -l`; клиент PostgreSQL уже входит
  в образ приложения (compose) или устанавливается на хост (systemd);
- медиа - хранилище напрямую, без промежуточной копии на диск: каталог
  `${STORAGE_ROOT}` при `STORAGE_TYPE=filesystem`, медиа-бакет при
  `STORAGE_TYPE=s3` (mc адресует его алиасом `MINIO_ALIAS`, rclone -
  remote `media`, собираемым из переменных `RCLONE_CONFIG_*`; rclone.conf
  для доступа к медиа-бакету не нужен).

## 2. Цели и их настройка

Цель - именованная запись в .env:

```text
BACKUP_TARGET_<ИМЯ>='<префикс>:<спецификация>'
```

Имя - заглавные буквы, цифры и подчеркивание (`^[A-Z_][A-Z0-9_]*$`).
Префикс выбирает инструмент копирования:

| Префикс | Спецификация | Инструмент |
| --- | --- | --- |
| `mc:` | `alias/бакет[/префикс]` | MinIO Client - S3/MinIO-цели |
| `rclone:` | `remote:путь` или локальный путь | rclone - диски и облачные хранилища |

Примеры:

```text
BACKUP_TARGET_OFFSITE='mc:local/backups'
BACKUP_TARGET_LOCALDISK='rclone:/mnt/backup'
BACKUP_TARGET_YADISK='rclone:yadisk:site-backup'
```

Раскладка внутри цели одинакова для обоих префиксов: дампы БД - `db/`,
медиа - `storage/`.

Новый механизм копирования добавляется плагином: подкласс `Target`
в [backend/backup/targets.py](../../backend/backup/targets.py) и запись
в реестре `TARGET_PREFIXES`; команды и оркестрация не меняются.

Единовременная настройка инструментов на сервере:

```bash
# mc: алиас для S3-целей (совпадает с MINIO_ALIAS для медиа-бакета
# или отдельный алиас для целей бэкапов)
mc alias set <алиас> <endpoint> <access-key> <secret-key>

# rclone: remote для облачных целей (Яндекс Диск, Google Drive, SFTP);
# локальные диски remote не требуют - указывается абсолютный путь
rclone config
```

Переменные окружения (секция «Бэкапы» .env):

- `BACKUP_DB_TARGETS`, `BACKUP_MEDIA_TARGETS` - списки целей;
- `MC_PATH` - путь к mc (только при наличии mc-целей);
- `BACKUP_DB_RETENTION_DAYS` - срок хранения дампов.

Шифрование бэкапов не используется (решение пользователя): инструменты
с обязательным шифрованием (restic) не подходят, файлы в целях остаются
обычными и читаются штатными средствами.

## 3. Семантика копирования

- Медиа - зеркальная синхронизация (`mc mirror --overwrite --remove` /
  `rclone sync`): объекты, исчезнувшие из хранилища, удаляются из целей.
  Отсутствие orphan-объектов - целевое поведение. Принятое следствие:
  зеркало не защищает медиа от случайного удаления - дампы БД медиа
  не содержат. Версионирование бакета осознанно не включается:
  noncurrent-версии тарифицируются на managed S3 без верхней границы,
  а медиафайлы пере-загружаемы из архива владельца.
- БД - датированные дампы `<база>_<дата>_<время>.dump` (UTC, например
  `personal_website_2026-08-25_1357.dump`), копируются в `db/` каждой
  цели списка; новые дампы не затирают предыдущие.
- Ретеншн: дампы старше `BACKUP_DB_RETENTION_DAYS` дней удаляются из
  целей и из локального `${BACKUP_ROOT}/db` при каждом бэкапе БД.

## 4. Команды

Все команды выполняются через хостовой вход (запуск из корня рабочей
копии на сервере):

```bash
bash scripts/backup.sh backup              # БД + медиа в настроенные цели
bash scripts/backup.sh backup --verify     # проверка целей без нового бэкапа
bash scripts/backup.sh backup_db           # только БД
bash scripts/backup.sh backup_media        # только медиа
bash scripts/backup.sh restore_db OFFSITE              # БД из последнего дампа цели
bash scripts/backup.sh restore_db /path/to/file.dump   # БД из локального файла
bash scripts/backup.sh restore_media OFFSITE           # медиа из storage/ цели
```

Проверка `--verify` для каждой активной цели:

- БД: наличие дампа моложе 25 часов, читаемость последнего дампа
  `pg_restore -l` конвейером (`mc cat` / `rclone cat` -> `pg_restore`)
  без выгрузки на диск;
- медиа: наличие содержимого `storage/`, сверка числа объектов
  с источником; зеркало полное, поэтому любое расхождение -
  предупреждение в журнале.

Непроверенные бэкапы равны их отсутствию: `--verify` предназначен
для аудита (скилл backup-audit). Учебное восстановление на тестовом
окружении - скилл restore-drill.

## 5. Расписание: cron и systemd timer

Основной механизм - host-cron через [scripts/cronjobs.sh](../../scripts/cronjobs.sh)
(добавляется установщиками): ежедневный запуск `backup` в 23:01, вывод -
в `${LOGS_ROOT}/backup.log`. Идемпотентен: повторный запуск не дублирует
задачу в crontab.

Альтернатива - systemd timer (догоняет пропущенные при выключенном
сервере запуски, логи в journal). Оба механизма равноправны, в scripts/
дублируется только cron. Юниты создаются вручную:

`/etc/systemd/system/personal-website-backup.service`:

```ini
[Unit]
Description=personal-website backup (db + media)

[Service]
Type=oneshot
User=<пользователь>
WorkingDirectory=/srv/personal-website
ExecStart=/bin/bash scripts/backup.sh backup
```

`/etc/systemd/system/personal-website-backup.timer`:

```ini
[Unit]
Description=Ежедневный запуск резервного копирования

[Timer]
OnCalendar=*-*-* 23:01:00
Persistent=true

[Install]
WantedBy=timers.target
```

Включение и проверка:

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now personal-website-backup.timer
systemctl list-timers personal-website-backup.timer
journalctl -u personal-website-backup.service --since today
```

При переходе с cron на timer удалить задачу из crontab (`crontab -e`),
чтобы копирование не выполнялось дважды.

## 6. Восстановление

При восстановлении с нуля (пустая БД + миграции) - сначала хранилище,
потом БД: миграция `gallery/0013` читает файлы через хранилище
и требует доступности медиа до запуска миграций.

1. Медиа: `bash scripts/backup.sh restore_media <ИМЯ>` - недеструктивное
   копирование из `storage/` цели (файлы хранилища, отсутствующие в цели,
   не удаляются);
2. БД: `bash scripts/backup.sh restore_db <ИМЯ>` - последний дамп цели
   конвейером в `pg_restore` (`--clean --if-exists`, объекты пересоздаются),
   либо `restore_db <путь>` для файла на диске; конкретный дамп цели -
   флагом `--dump <имя>`;
3. Проверка целостности - счетчики таблиц и примененные миграции
   (скилл postgresql-restore).

Восстановление на новом сервере выполняется до переключения DNS;
живость после восстановления проверяется эндпоинтом `/health/`.

## 7. Смена типа хранилища

Перенос медиа между бэкендами (filesystem <-> S3) выполняется командами
бэкапов через временную цель, отдельный механизм переноса в кодовой базе
не заводится:

1. Добавить в .env временную цель, например
   `BACKUP_TARGET_TRANSFER='rclone:/mnt/transfer'`, и включить её имя
   в `BACKUP_MEDIA_TARGETS`;
2. `bash scripts/backup.sh backup_media` - зеркальная синхронизация
   текущего хранилища в цель;
3. Изменить `STORAGE_TYPE` и параметры хранилища в .env, перезапустить
   приложение;
4. `bash scripts/backup.sh restore_media TRANSFER` - копирование
   в новое хранилище;
5. Проверить число объектов (`backup_media --verify` после добавления
   постоянных целей) и удалить временную цель из .env.

## 8. Правило 3-2-1 и защита целей

Правило 3-2-1: три копии данных (оригинал и две цели бэкапа), два
разных места хранения, одна копия вне сервера (offsite).

- Минимум две цели, одна - offsite (не тот же сервер). Для домашнего
  сервера offsite-цель обязательна: «бэкап на другом диске того же
  сервера» offsite не считается.
- У offsite-цели - учетные данные, независимые от приложения
  (компрометация хоста не должна уничтожать доступные на запись цели).
- Для S3-цели - отдельный пользователь с минимальными правами на бакет
  бэкапов.
- Оригиналы медиа пере-загружаемы из архива владельца; критичные
  для восстановления данные - датированные дампы БД в целях
  и `acme.json` прокси-слоя (см. [proxy.md](./proxy.md)).
