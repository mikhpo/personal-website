# Резервное копирование

Конфигурация бэкапов выбирается независимо от остальных параметров развертывания (способ запуска приложения, база данных, хранилище, прокси). Система реализована Django-приложением `backend/backup/` с management-командами. Хостовой вход - [scripts/backup.sh](../../scripts/backup.sh), диспетчеризующий по DEPLOY_MODE: compose - исполнение в контейнере application, systemd - интерпретатор виртуального окружения на хосте. Работа полностью неинтерактивна: без паролей и подтверждений, поэтому годится для cron и systemd timer.

## 1. Конфигурация: одна переменная

Все бэкапирование настраивается одной переменной .env - списком адресов целей через пробел:

```text
BACKUP_TARGETS='yadisk:site-backup /mnt/backup'
```

База данных и медиа копируются во все перечисленные места; пустое значение отключает бэкапирование (в режиме `--verify` считается ошибкой настройки).

Источник читается напрямую, без промежуточной копии на диск. База данных снимается дампом `pg_dump -Fc` в локальный каталог `${BACKUP_ROOT}/db/` с проверкой читаемости `pg_restore -l`. Клиент PostgreSQL уже входит в образ приложения (compose) или устанавливается на хост (systemd). Медиа копируются из хранилища напрямую: каталог `${STORAGE_ROOT}` при `STORAGE_TYPE=filesystem`, медиа-бакет при `STORAGE_TYPE=s3` (rclone remote `media`, собираемый из переменных `RCLONE_CONFIG_*`; rclone.conf для доступа к медиа-бакету не нужен).

## 2. Адреса целей и новые способы

Адрес цели - локальный путь (`/mnt/backup`) либо rclone-адрес (`remote:путь`, где remote настроен в rclone.conf хоста: Яндекс Диск, Google Drive, SFTP, S3). Раскладка внутри цели одинакова: дампы БД лежат в `db/`, медиа - в `storage/`.

Новое место назначения не требует правок кода: это новый remote в rclone.conf или локальный путь в `BACKUP_TARGETS`. Remote настраивается на сервере один раз (`rclone config`; локальные диски remote не требуют). В Docker Compose команды бэкапов выполняются внутри контейнера application, rclone.conf монтируется или remotes собираются переменными `RCLONE_CONFIG_*`.

Новый инструмент копирования (если rclone перестанет устраивать) добавляется тремя шагами:

1. функции операций для адресов своего вида - по образцу rclone-функций в [backend/backup/services.py](../../backend/backup/services.py): `push_dump`, `dumps`, `restore_db`, `prune_dumps`, `has_fresh_dump`, `media_count`, `sync_media`, `pull_media`;
2. ветка по виду адреса в этих функциях (например, адрес с префиксом инструмента направляется в его функции);
3. тесты нового инструмента на реальных операциях по образцу существующих в backend/backup/tests/.

Переменные окружения (секция "Бэкапы" .env):

- `BACKUP_TARGETS` - адреса целей;
- `BACKUP_DB_RETENTION_DAYS` - срок хранения дампов.

Шифрование бэкапов не используется (решение пользователя): инструменты с обязательным шифрованием (restic) не подходят, файлы в целях остаются обыными и читаются штатными средствами.

## 3. Семантика копирования

Медиа копируются зеркальной синхронизацией (`rclone sync`): объекты, исчезнувшие из хранилища, удаляются из целей, поэтому orphan-объектов в целях не накапливается - это целевое поведение. Принятое следствие: зеркало не защищает медиа от случайного удаления, а дампы БД медиа не содержат. Версионирование бакета осознанно не включается: noncurrent-версии тарифицируются на managed S3 без верхней границы, а медиафайлы пере-загружаемы из архива владельца.

База данных копируется датированными дампами `<база>_<дата>_<время>.dump` (МСК, например `personal_website_2026-08-25_1657.dump`): они раскладываются в `db/` каждой цели списка, и новые дампы не затирают предыдущие.

Ретеншн управляет хранением: дампы старше `BACKUP_DB_RETENTION_DAYS` дней удаляются из целей и из локального `${BACKUP_ROOT}/db` при каждом бэкапе БД.

## 4. Команды

Все команды выполняются через хостовой вход - из корня рабочей копии на сервере:

```bash
bash scripts/backup.sh backup                          # БД + медиа во все цели
bash scripts/backup.sh backup --verify                 # проверка целей без нового бэкапа
bash scripts/backup.sh restore db yadisk:site-backup   # БД из последнего дампа цели
bash scripts/backup.sh restore db /path/to/file.dump   # БД из локального файла дампа
bash scripts/backup.sh restore media yadisk:site-backup # медиа из storage/ цели
```

Проверка `--verify` проходит по каждой активной цели. Для БД она проверяет наличие дампа моложе 25 часов и читаемость последнего дампа `pg_restore -l` конвейером (`rclone cat` -> `pg_restore`) без выгрузки на диск. Для медиа - наличие содержимого `storage/` и сверку числа объектов с источником: зеркало полное, любое расхождение попадает в журнал как предупреждение.

Непроверенные бэкапы равны их отсутствию: `--verify` предназначен для аудита (скилл backup-audit). Учебное восстановление на тестовом окружении выполняет отдельный скилл restore-drill.

## 5. Расписание: cron и systemd timer

Основной механизм - cron хоста через [scripts/cronjobs.sh](../../scripts/cronjobs.sh) (добавляется установщиками): ежедневный запуск `backup` в 23:01 МСК, вывод - в `${LOGS_ROOT}/backup.log`. Время в crontab интерпретируется в системной таймзоне хоста - установщики фиксируют ее значением Europe/Moscow (scripts/server/setup.sh, scripts/docker/setup.sh). Добавление идемпотентно: повторный запуск не дублирует задачу в crontab.

Альтернатива - systemd timer: он догоняет пропущенные при выключенном сервере запуски и пишет логи в journal. Механизмы равноправны, в scripts/ дублируется только cron. Юниты создаются вручную. Время OnCalendar, как и у cron, задается в системной таймзоне хоста.

`/etc/systemd/system/personal-website-backup.service`:

```ini
[Unit]
Description=personal-website backup (db + media)

[Service]
Type=oneshot
User=<пользователь>
WorkingDirectory=/srv/personal-website
ExecStart=/bin/bash scripts/backup.sh backup
```

`/etc/systemd/system/personal-website-backup.timer`:

```ini
[Unit]
Description=Ежедневный запуск резервного копирования

[Timer]
OnCalendar=*-*-* 23:01:00
Persistent=true

[Install]
WantedBy=timers.target
```

Включение и проверка:

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now personal-website-backup.timer
systemctl list-timers personal-website-backup.timer
journalctl -u personal-website-backup.service --since today
```

При переходе с cron на timer удалить задачу из crontab (`crontab -e`), чтобы копирование не выполнялось дважды.

## 6. Восстановление

При восстановлении с нуля (пустая база плюс миграции) медиа должны быть доступны до запуска миграций: миграция `gallery/0013` читает файлы через хранилище. В таком сценарии восстанавливать сначала хранилище, потом базу.

1. Медиа: `bash scripts/backup.sh restore media <адрес>` - недеструктивное копирование из `storage/` цели (файлы хранилища, отсутствующие в цели, не удаляются).
2. База: `bash scripts/backup.sh restore db <адрес>` - последний дамп цели в `pg_restore` (`--clean --if-exists`, объекты пересоздаются), либо `restore db <путь>` для файла на диске. Конкретный дамп цели выбирается флагом `--dump <имя>`.
3. Целостность проверяется счетчиками таблиц и примененными миграциями (скилл postgresql-restore).

Восстановление на новом сервере выполняется до переключения DNS. Работоспособность после восстановления подтверждается эндпоинтом `/health/`.

## 7. Смена типа хранилища

Перенос медиа между бэкендами (filesystem <-> S3) выполняется командами бэкапов: старое хранилище служит источником, новое - приемником, а мостом между ними выступают постоянные цели бэкапов. Медиа-бакет в S3-режиме хранит медиа в префиксе `media/`, поэтому цели получают чистую медиатеку без статики.

1. На старом хранилище выполнить `bash scripts/backup.sh backup` - текущее хранилище зеркально синхронизируется в настроенные цели (`BACKUP_TARGETS`).
2. Изменить `STORAGE_TYPE` и параметры хранилища в .env и перезапустить приложение - хранилище теперь новое и пустое.
3. Выполнить `bash scripts/backup.sh restore media <адрес>` - медиа из выбранной цели копируются в новое хранилище.
4. Проверить число объектов (`backup --verify`) и работать с настроенными целями дальше: переконфигурация целей не требуется.

Для перехода в обратную сторону процедура повторяется в обратном порядке с теми же целями.

## 8. Правило 3-2-1 и защита целей

Правило 3-2-1: три копии данных (оригинал и две цели бэкапа), два разных места хранения, одна копия вне сервера (offsite).

Техническое ограничение одно: хотя бы одна цель должна быть offsite, то есть не на том же сервере, - "бэкап на другом диске того же сервера" offsite не считается. Число целей сверх этого - рекомендация по правилу 3-2-1, а не техническое требование: сколько целей вести на каждом этапе развития проекта, решает администратор. У offsite-цели - учетные данные, независимые от приложения: компрометация хоста не должна уничтожать доступные на запись цели. Для S3-цели заводится отдельный пользователь с минимальными правами на бакет бэкапов.

Критичные для восстановления данные - только датированные дампы БД в целях: оригиналы медиа пере-загружаемы из архива владельца, а сертификаты прокси выпускаются и продлеваются certbot автоматически ([proxy.md](./proxy.md)).

## 9. Оповещения о результатах

Каждый реальный запуск команды backup сопровождается письмом-отчетом на адрес BACKUP_NOTIFY_EMAIL. Проверка целей (--verify) уведомлений не создает. Восстановление отчетами не покрывается: это редкая ручная операция, результат виден оператору сразу.

Отчет содержит имя команды, хост, время начала (МСК) и длительность. При успехе в отчет входят разделы "База данных" (цели, имя и объем дампа, ретеншн) и "Медиа" (цели, число объектов и объем хранилища) - только по тому, что делала команда. При ошибке разделов нет: письмо содержит полный журнал команды. Запуск с ненастроенными целями письмом не сопровождается: бэкапирование не выполнялось.

Отправка выполняется штатным django send_mail от адреса DEFAULT_FROM_EMAIL. Пустое значение BACKUP_NOTIFY_EMAIL отключает оповещения. Отказ почтового сервера не меняет код возврата команды - в журнал пишется предупреждение, бэкап считается выполненным. Первый реальный прогон с доставкой письма проверяется на продакшен-сервере письмом через django shell.
