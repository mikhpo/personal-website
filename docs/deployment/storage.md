# Файловое хранилище

Тип хранилища медиафайлов выбирается независимо от остальных параметров
развертывания. Варианты: filesystem на подключенном диске / S3 удаленный
(провайдер) / MinIO локальный (контейнер compose, профиль minio).
Переключатель - переменная `STORAGE_TYPE` (`filesystem` - дефолт, `s3`),
параметры S3 - переменные `AWS_*`.

Содержание:

1. filesystem
2. S3 и локальный MinIO
3. Статика
4. Миниатюры ImageKit
5. Перенос между типами хранилища

## 1. filesystem

Медиа - файлы в каталоге `${STORAGE_ROOT}` (в контейнере путь задает
compose.yaml, на хосте - переменная из .env). Каталог размещается на
подключенном диске выбором пути. Инфраструктура не требуется: профиль
minio не активируется, статика раздается WhiteNoise.

## 2. S3 и локальный MinIO

При `STORAGE_TYPE='s3'` приложение работает с бакетом через переменные:

- `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` - ключи доступа;
- `AWS_STORAGE_BUCKET_NAME` - бакет медиа;
- `AWS_S3_REGION_NAME` - регион;
- `AWS_S3_ENDPOINT_URL` - эндпоинт S3-совместимого сервиса.

Удаленный S3 провайдера требует собственных ключей и бакета. Локальный
MinIO поднимается профилем minio (`docker compose up -d minio`):
админ-консоль - `MINIO_ROOT_USER/ROOT_PASSWORD` (порты 9000/9001
публикуются только на 127.0.0.1), ключи приложения - `MINIO_ACCESS_KEY/
SECRET_KEY`, эндпоинт `AWS_S3_ENDPOINT_URL='http://127.0.0.1:9000'`.
Данные MinIO живут в именованном томе `minio-data` (переживает
`docker compose down`, удаляется `down -v`).

При STORAGE_TYPE=s3 entrypoint ожидает готовность эндпоинта
`AWS_S3_ENDPOINT_URL` TCP-проверкой перед миграциями (сервис может быть
внешним, depends_on не используется); при filesystem ожидания нет.

Медиа-бакет адресуется инструментами бэкапов: mc - алиасом `MINIO_ALIAS`
(настраивается на сервере `mc alias set`), rclone - remote `media`,
собираемым приложением из переменных `RCLONE_CONFIG_*` без rclone.conf
(см. [backups.md](./backups.md)).

## 3. Статика

Статические файлы обслуживаются тем же слоем, что и медиа:

- filesystem: сбор `collectstatic` в `${STATIC_ROOT}`, раздача
  WhiteNoise (сжатие и хеширование имен, прокси о статике не знает);
- s3: collectstatic складывает статику в префикс `static/` того же
  бакета, WhiteNoise отключается; `STATIC_URL` и `WEBPACK_PUBLIC_PATH`
  указывают на адрес бакета/CDN с префиксом `static/`, например
  `https://storage.yandexcloud.net/<бакет>/static/`.

Бандлам webpack с хешем содержимого в имени назначается бессрочное
кэширование (`Cache-Control: immutable`), остальной статике - умеренный
срок (заголовки задает хранилище при загрузке).

## 4. Миниатюры ImageKit

Миниатюры галереи генерируются ImageKit по первому обращению
(стратегия Optimistic) и сохраняются в активное хранилище: при
filesystem - в тот же каталог, при s3 - в тот же бакет. Последствия:

- первый запрос каждой миниатюры дороже последующих;
- при переносе хранилища кэш миниатюров переносится вместе с медиа
  (или перегенерируется по первому обращению - потери данных нет).

## 5. Перенос между типами хранилища

Смена `STORAGE_TYPE` на существующих данных выполняется командами
системы бэкапов через временную цель `BACKUP_TARGET_<ИМЯ>`:
синхронизация текущего хранилища в цель, переключение переменных,
восстановление в новое хранилище, сверка числа объектов. Пошаговая
процедура - [backups.md](./backups.md), раздел 7. Отдельный механизм
переноса в кодовой базе не заводится.
