# Файловое хранилище

Тип хранилища медиафайлов выбирается независимо от остальных параметров развертывания. Варианты: filesystem на подключенном диске, удаленный S3 провайдера или локальный сервер RustFS (контейнер compose, профиль s3). Переключатель - переменная `STORAGE_TYPE` (`filesystem` - дефолт, `s3`), параметры S3 - переменные `AWS_*`.

## 1. filesystem

Медиафайлы хранятся в каталоге `${STORAGE_ROOT}`: в контейнере путь задает compose.yaml, на хосте - переменная из .env. Размещение каталога на подключенном диске выбирается просто заданием пути. Инфраструктура не требуется: профиль s3 не активируется, статика раздается WhiteNoise.

Раздача медиа зависит от типа хранилища и окружения. При filesystem и DEBUG=True файлы обслуживает сервер разработки Django по адресу /media/. Разработка не обязана вестись с filesystem: допустим и `STORAGE_TYPE='s3'` с локальным RustFS или удаленным S3 - тогда медиа и статику отдает объектное хранилище. В продакшене при filesystem медиа раздает прокси-сервер напрямую с диска, минуя воркеры приложения: хостовой и контейнерный nginx делают это одинаково - location /media/ с alias на `STORAGE_ROOT` ([proxy.md](./proxy.md), разделы 2 и 3), в контейнере каталог хранилища монтируется прямо в прокси read-only.

## 2. S3 и локальный RustFS

При `STORAGE_TYPE='s3'` приложение работает с бакетом через переменные:

- `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` - ключи доступа;
- `AWS_STORAGE_BUCKET_NAME` - бакет медиа;
- `AWS_S3_REGION_NAME` - регион;
- `AWS_S3_ENDPOINT_URL` - эндпоинт S3-совместимого сервиса.

Удаленный S3 провайдера требует собственных ключей и бакета. Локальный сервер RustFS поднимается профилем s3 (`docker compose up -d s3`): образ следует плавающему тегу latest, чтобы изменения сервера приходили своевременно, а регрессии ловили S3-тесты; порты API (9000) и веб-консоли (9001) публикуются только на 127.0.0.1. Ключи приложения (`AWS_ACCESS_KEY_ID/SECRET_ACCESS_KEY`) передаются серверу теми же переменными, эндпоинт приложения - `AWS_S3_ENDPOINT_URL='http://s3:9000'` (адрес из сети Compose; для сервера на хосте - `http://127.0.0.1:9000`). Данные живут в именованном томе s3-data: он переживает `docker compose down` и удаляется `down -v`.

Веб-консоль сервера открывается по адресу `http://127.0.0.1:9001/rustfs/console/index.html` (публикация только на localhost хоста). Учетные данные для входа - те же ключи доступа S3, что приложение передает серверу: в поле Account вводится значение переменной `AWS_ACCESS_KEY_ID` из .env, в поле Key - `AWS_SECRET_ACCESS_KEY`; отдельных пользователей для консоли не заводится. Консоль дает браузер бакетов и объектов, управление ключами, пользователями и политиками; консоль встроена в сервер и отключается переменной `RUSTFS_CONSOLE_ENABLE=false` (в проекте не отключается).

Бакет и публичная раздача инициализируются при старте приложения командой `manage.py init_s3` (entrypoint контейнера и ExecStartPre systemd-юнита, перед миграциями; вне STORAGE_TYPE=s3 команда завершается без действий). Правило собственности: бакета нет - создать и применить bucket policy (анонимное чтение префиксов `media/` и `static/`); бакет существует - не выполнять ни одной изменяющей операции. Внешний провайдер настраивается до первого старта приложения, поэтому политики внешних бакетов приложению недоступны: публичность объектов на object-ACL-провайдерах обеспечивает ACL public-read при каждой загрузке и при копировании внутри бакета (смена альбома фотографии). Провайдер обязан поддерживать одно из двух - canned ACL на загрузках и копировании либо bucket policy; хранилища с принудительно отключенными ACL (режим bucket-owner-enforced) работают только через политику бакета. Следствие правила собственности: опечатка в имени бакета против внешнего провайдера проявится пустым свежесозданным бакетом, а не отказом NoSuchBucket.

Локальный сервер выбран сравнением живыми прогонами восьми S3-кандидатов (совместимость, ресурсность, лицензии, поднимаемость): зафиксирован RustFS 1.0.1 с моделью публичной раздачи bucket policy. Предыстория перехода, матрица сравнения и мотивация - в комментарии-решении к задаче #117 на SourceCraft; краткая выжимка - в CHANGELOG.

Внутри бакета медиа и статика разделены по корневым каталогам: медиа - в префиксе `media/`, статика - в `static/`. Разделение делает адресацию прозрачной: резервное копирование медиа работает с префиксом `media/` и не затрагивает статику, а статику в любой момент можно пересобрать `collectstatic` без переноса данных.

Бакет, созданный до введения префиксов, переводится на новую раскладку однократным переносом объектов rclone (медиа из корня в `media/`, статика остается в `static/`).

При STORAGE_TYPE=s3 entrypoint перед миграциями ждет готовность эндпоинта `AWS_S3_ENDPOINT_URL` TCP-проверкой (сервис может быть внешним, depends_on не используется), запускает `manage.py init_s3` (инициализация нового хранилища по правилу собственности, см. выше) и выполняет миграции; при filesystem ожидания нет.

Медиа-хранилище адресуется инструментами бэкапов через rclone remote `media`, который приложение собирает из переменных `RCLONE_CONFIG_*` без rclone.conf ([backups.md](./backups.md)).

## 3. Статика

Статические файлы обслуживает тот же слой, что и медиа:

- при filesystem - сбор `collectstatic` в `${STATIC_ROOT}` и раздача WhiteNoise (сжатие и хеширование имен, прокси о статике не знает);
- при s3 - collectstatic складывает статику в префикс `static/` бакета (медиа живут в префиксе `media/` того же бакета), WhiteNoise отключается. `STATIC_URL` и `WEBPACK_PUBLIC_PATH` указывают на адрес бакета или CDN с префиксом `static/`, например `https://storage.yandexcloud.net/<бакет>/static/`.

Бандлам webpack с хешем содержимого в имени назначается бессрочное кэширование (`Cache-Control: immutable`), остальной статике - умеренный срок, заголовки задает хранилище при загрузке.

## 4. Миниатюры ImageKit

Производные версии фотографий галереи - миниатюра 500px и превью 1000px - генерирует django-imagekit из оригинала и складывает в активное хранилище, в каталог `CACHE/images`: при filesystem - в тот же каталог, при s3 - в тот же бакет. Генерация выполняется фоновым воркером сразу после загрузки фотографии, замены изображения или смены альбома; при filesystem-хранилище запись атомарна (временный файл замещает целевой одной операцией), и прямая раздача медиа прокси не видит файлов в промежуточном состоянии. Актуальный кэш не перегенерируется: если кэш-файл новее исходника, задача пропускает его. Если воркер не успел или не справился, миниатюра генерируется синхронно при первом обращении - так посетители никогда не видят битых миниатюр. При переносе хранилища кэш миниатюр переезжает вместе с медиа или перегенерируется по первому обращению - потери данных нет. Подробнее - [worker.md](./worker.md).

## 5. Перенос между типами хранилища

Смена `STORAGE_TYPE` на существующих данных выполняется командами системы бэкапов: синхронизация текущего хранилища в цели (`backup_media`), переключение переменных, восстановление из цели в новое хранилище (`restore_media <ИМЯ>`), сверка числа объектов. Источник и приемник - хранилища, мостом служат постоянные цели бэкапов. Пошаговая процедура описана в [backups.md](./backups.md), раздел 7. Отдельный механизм переноса в кодовой базе не заводится.
