# Файловое хранилище

Тип хранилища медиафайлов выбирается независимо от остальных параметров
развертывания. Варианты: filesystem на подключенном диске, удаленный
S3 провайдера или локальный MinIO (контейнер compose, профиль minio).
Переключатель - переменная `STORAGE_TYPE` (`filesystem` - дефолт,
`s3`), параметры S3 - переменные `AWS_*`.

## 1. filesystem

Медиафайлы хранятся в каталоге `${STORAGE_ROOT}`: в контейнере путь
задает compose.yaml, на хосте - переменная из .env. Размещение каталога
на подключенном диске выбирается просто заданием пути. Инфраструктура
не требуется: профиль minio не активируется, статика раздается
WhiteNoise.

Раздача медиа зависит от типа хранилища и окружения. При filesystem
и DEBUG=True файлы обслуживает сервер разработки Django по адресу
/media/. Разработка не обязана вестись с filesystem: допустим
и `STORAGE_TYPE='s3'` с локальным MinIO или удаленным S3 - тогда
медиа и статику отдает объектное хранилище. В продакшене
при filesystem медиа раздает прокси-сервер напрямую с диска, минуя
воркеры приложения: хостовой и контейнерный nginx делают это
одинаково - location /media/ с alias на `STORAGE_ROOT`
([proxy.md](./proxy.md), разделы 2 и 3), в контейнере каталог
хранилища монтируется прямо в прокси read-only.

## 2. S3 и локальный MinIO

При `STORAGE_TYPE='s3'` приложение работает с бакетом через переменные:

- `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` - ключи доступа;
- `AWS_STORAGE_BUCKET_NAME` - бакет медиа;
- `AWS_S3_REGION_NAME` - регион;
- `AWS_S3_ENDPOINT_URL` - эндпоинт S3-совместимого сервиса.

Удаленный S3 провайдера требует собственных ключей и бакета. Локальный
MinIO поднимается профилем minio (`docker compose up -d minio`):
админ-консоль настраивается переменными `MINIO_ROOT_USER/ROOT_PASSWORD`
(порты 9000/9001 публикуются только на 127.0.0.1), ключи приложения -
`MINIO_ACCESS_KEY/SECRET_KEY`, эндпоинт -
`AWS_S3_ENDPOINT_URL='http://127.0.0.1:9000'`. Данные MinIO живут
в именованном томе minio-data: он переживает `docker compose down`
и удаляется `down -v`.

При STORAGE_TYPE=s3 entrypoint перед миграциями ждет готовность
эндпоинта `AWS_S3_ENDPOINT_URL` TCP-проверкой (сервис может быть
внешним, depends_on не используется); при filesystem ожидания нет.

Медиа-бакет адресуется и инструментами бэкапов: mc - алиасом
`MINIO_ALIAS` (настраивается на сервере командой `mc alias set`),
rclone - remote `media`, который приложение собирает из переменных
`RCLONE_CONFIG_*` без rclone.conf ([backups.md](./backups.md)).

## 3. Статика

Статические файлы обслуживает тот же слой, что и медиа:

- при filesystem - сбор `collectstatic` в `${STATIC_ROOT}` и раздача
  WhiteNoise (сжатие и хеширование имен; прокси о статике не знает);
- при s3 - collectstatic складывает статику в префикс `static/` того
  же бакета, WhiteNoise отключается; `STATIC_URL`
  и `WEBPACK_PUBLIC_PATH` указывают на адрес бакета или CDN
  с префиксом `static/`, например
  `https://storage.yandexcloud.net/<бакет>/static/`.

Бандлам webpack с хешем содержимого в имени назначается бессрочное
кэширование (`Cache-Control: immutable`), остальной статике - умеренный
срок; заголовки задает хранилище при загрузке.

## 4. Миниатюры ImageKit

Миниатюры галереи генерируются ImageKit по первому обращению (стратегия
Optimistic) и сохраняются в активное хранилище: при filesystem - в тот
же каталог, при s3 - в тот же бакет. Первый запрос каждой миниатюры
дороже последующих. При переносе хранилища кэш миниатюр переезжает
вместе с медиа или перегенерируется по первому обращению - потери
данных нет.

## 5. Перенос между типами хранилища

Смена `STORAGE_TYPE` на существующих данных выполняется командами
системы бэкапов через временную цель `BACKUP_TARGET_<ИМЯ>`:
синхронизация текущего хранилища в цель, переключение переменных,
восстановление в новое хранилище, сверка числа объектов. Пошаговая
процедура описана в [backups.md](./backups.md), раздел 7. Отдельный
механизм переноса в кодовой базе не заводится.
