# Воркер фоновых задач

Превью и миниатюры фотографий генерируются не в момент HTTP-запроса, а фоновым воркером сразу после загрузки. Воркер - это процесс-потребитель очереди фоновых задач: он ждет новые задачи в таблице очереди и выполняет их один за другим с ограниченным параллелизмом. Вынесение обработки изображений из web-воркеров ускоряет загрузку фотографий и изолирует расход памяти Pillow: web-воркеры перестают выполнять ресурсоемкие ресайзы.

## 1. Архитектура

Задачи объявлены на фреймворке django.tasks, входящем в ядро Django 6.0: декоратор `@task` из `django.tasks`, постановка в очередь методом `enqueue()`. Задача генерации - `gallery/tasks.py`, `generate_photo_images(photo_pk)`. Она генерирует обе производные версии фотографии (миниатюру 500px и превью 1000px) и идемпотентна: актуальный кэш-файл (созданный позже исходника) не перезаписывается, отсутствующий или устаревший создается атомарной заменой, а фотография, удаленная до выполнения задачи, пропускается.

Триггер - сигнал `post_save` модели Photo (`gallery/signals.py`, подключается в `gallery/apps.py`). Задача ставится в очередь при создании фотографии, замене изображения и смене альбома с перемещением файла. Частичные сохранения прочих полей (EXIF, taken_at, название) задачу не порождают: приемник фильтрует события по `update_fields`.

Транспортом служит очередь huey в существующем кластере PostgreSQL - бэкенд `huey.contrib.djhuey.tasks_backend.HueyBackend` из настроек `TASKS`. Постановка задачи отложена до коммита транзакции (`ENQUEUE_ON_COMMIT: True`), поэтому воркер не видит незакоммиченные строки. Хранилище очереди - `huey.PostgresHuey` (настройка `HUEY`): таблицы очереди живут в той же базе, что и данные приложения, отдельный брокер не нужен. Соединение открывается лениво, поэтому импорт настроек в тестах и CI не требует доступного PostgreSQL.

Отказ постановки задачи (недоступная очередь, отсутствие таблиц) не прерывает сохранение фотографии: отказ записывается в журнал, а миниатюры будут сгенерированы при первом обращении к ним. Если воркер недоступен, система деградирует так же мягко: задачи копятся в таблице очереди и выполняются после его восстановления, а до тех пор миниатюры генерируются синхронно при первом обращении - встроенной стратегией JustInTime библиотеки django-imagekit. Посетители не видят битых миниатюр ни при каких обстоятельствах.

## 2. Запуск

Воркер запускается командой `manage.py run_huey` тем же образом приложения, что и веб-сервер. Схему базы данных - миграции Django и таблицы очереди huey - создает только веб-сервис при старте, поэтому порядок старта значим: воркер стартует после готовности веб-сервиса.

- Docker Compose - сервис `worker` в compose.yaml. Тот же образ и entrypoint.sh, но переменная `RUN_MODE=worker` переключает запуск с веб-сервера на run_huey после ожидания инфраструктуры. Зависимость `depends_on: application: condition: service_healthy` запускает воркер после того, как веб-сервис применил миграции и создал таблицы очереди. Порты и healthcheck воркеру не нужны - HTTP он не обслуживает, супервизию выполняет `restart: always`.
- systemd - юнит personal-website-worker.service, рендерится setup.sh из шаблона scripts/server/systemd/personal-website-worker.service.template по тем же переменным WORK_DIR и SERVICE_USER. Директива After=personal-website.service задает старт после веб-юнита, в чьих ExecStartPre выполняются миграции и создание таблиц очереди; перезапуск при сбое - Restart=on-failure.
- Локальная разработка - `task worker` (Taskfile) либо вручную `poetry run python ./backend/manage.py run_huey`; задача сама создает таблицы очереди командой create_huey_tables. При `DEBUG=True` задачи исполняются синхронно в процессе сервера разработки (режим immediate huey), и отдельный воркер не нужен.

Число и тип потребителей настраиваются переменными `HUEY_WORKERS` (по умолчанию 2) и `HUEY_WORKER_TYPE` (по умолчанию `process` - ресайзы нагружают процессор, для них выгоднее процессы, а не потоки).

## 3. Наблюдаемость

В админке Django доступен дашборд очереди: глубина очереди, выполняющиеся задачи, статистика по задачам, журнал событий с ошибками, управление - повтор постановки и очистка. Приложение статистики `huey.contrib.djhuey.stats` включено только вне тестов и разработки. Статистика пишется в PostgreSQL рядом с данными приложения (настройка `HUEY_STATS`), ее таблицы создает и чистит сама библиотека.

Журнал воркера в контейнерном режиме собирает Docker logging driver (json-file с ротацией, как у остальных сервисов), в systemd-режиме - journal: `journalctl -u personal-website-worker -f`.

## 4. Тесты

В тестовом окружении (`TEST=True`, pytest и CI) настройка `TASKS` переключается на встроенный ImmediateBackend: задачи выполняются инлайн в момент постановки, без воркера и очереди - тесты проверяют реальную генерацию файлов на тестовом хранилище без подмен и без запуска потребителей. Приложение статистики в тестах исключено из INSTALLED_APPS.
