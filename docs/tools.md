# Инструменты разработчика

Каталог `tools/` содержит вспомогательные скрипты рабочего процесса разработки. Инструменты тестирования, генерации схем моделей и рендера диаграмм (run-tests.sh, graph-models.sh, render-diagrams.sh) описаны в [CONTRIBUTING.md](./CONTRIBUTING.md); этот документ - о синхронизации зеркал репозитория.

## Синхронизация зеркал репозитория

Разработка ведется параллельно в двух git-хостингах: GitHub и SourceCraft (оба - mikhpo/personal-website). Коммит, попавший в main одного хостинга, не переносится на другой автоматически, поэтому зеркала синхронизирует специальный скрипт: он выравнивает main и теги всех зеркал в обе стороны без выделенного главного репозитория. Список зеркал - константа PEERS внутри скрипта; подключение новой платформы сводится к новой записи списка и настройке SSH-ключей.

Скрипт существует в двух эквивалентных реализациях с одинаковым алгоритмом:

    bash tools/sync-mirrors.sh
    poetry run python tools/sync_mirrors.py

Аргументов и флагов нет. Для запуска с локальной машины достаточно SSH-доступа к обоим хостингам; при запуске в CI аутентификацию настраивает обертка workflow, логике скрипта ключи и переменные окружения не нужны.

### Алгоритм

Скрипт работает во временном bare-репозитории и не затрагивает рабочую копию:

1. Получить main и теги каждого зеркала fetch-ем в namespaced-рефы refs/sync/<зеркало>/.
2. Синхронизировать main: вершина - состояние, потомком которого являются состояния всех остальных зеркал. Отстающим зеркалам вершина доставляется обычным push-ем (только fast-forward, без force); зеркала с равным состоянием не трогаются. Push получает только отстающий хостинг, поэтому платформа, запустившая синхронизацию, не обращается к самой себе.
3. Синхронизировать теги: у каждого имени тега состояния всех знающих его зеркал должны совпадать; отсутствующим зеркалам тег доставляется push-ем от знающего.
4. Удаления рефов не выполняются ни для веток, ни для тегов; чистка устаревших рефов - только вручную.

Политика расхождения - только fast-forward. Если ни одно состояние main не является потомком остальных либо одно имя тега имеет разные состояния, скрипт завершается с диагностикой, ничего не меняя; расхождение разрешает человек локально (git merge-base, merge одной стороны в другую), затем запуск повторяется. Рабочее соглашение: каждое изменение мержится ровно на одной платформе, вторая получает его синхронизацией; дублирующий merge на обеих платформах уронит синк с диагностикой.

### Коды выхода

- 0 - зеркала синхронны либо доставка выполнена успешно
- 1 - расхождение main или конфликт тега; требуется ручное разрешение
- 2 - операционная ошибка git или сети
