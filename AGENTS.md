# AGENTS.md

## Обзор проекта

Персональный сайт на Django с React-фронтендом: блог, фотогалерея, учетные записи пользователей, панель администратора. Цели: функциональность, расширяемость и модульность, высокое качество кода, полная документация для дальнейшей разработки.

## Команды

### Установка и запуск

- Установить зависимости Python: `poetry install`
- Установить зависимости Node.js: `npm install`
- Применить миграции: `poetry run python backend/manage.py migrate`
- Собрать статические файлы: `poetry run python backend/manage.py collectstatic --no-input`
- Запустить сервер разработки: `poetry run python backend/manage.py runserver`
- Запустить тесты: `poetry run pytest`

### Docker Compose

- Использовать V2 `docker compose` или V1 `docker-compose`
- `docker compose up -d` - запустить приложение с зависимостями
- Каждый инфраструктурный сервис в собственном профиле: postgres, minio, nginx
- Набор сервисов определяет `COMPOSE_PROFILES` в `.env`
- Локальной разработке обычно достаточно профиля postgres с файловым хранилищем
- minio - при разработке с S3-хранилищем
- nginx - при отладке прокси-слоя
- `docker compose up -d postgres minio` - только база данных и объектное хранилище (имя сервиса активирует профиль автоматически)
- `docker compose down` - остановить приложение и зависимости (только сервисы активных профилей)
- Включение S3-хранилища: переменная `STORAGE_TYPE=s3` и MinIO через Compose
- В окружениях с внешней инфраструктурой `COMPOSE_PROFILES` не задавать
- Диагностические команды адресовать только сервисам application и nginx (`up -d postgres` поднял бы сервис профиля postgres)

### Taskfile

Стандартные задачи разработки (полный перечень - в `Taskfile.yml`):

- `task install` - установить зависимости
- `task runserver` - запустить сервер разработки
- `task test` - запустить тесты
- `task check` - выполнить статический анализ и проверки Django
- `task migrate` - создать и применить миграции
- `task pre-commit` - выполнить pre-commit хуки

Комплексные операции объединены в одну команду, Docker-контейнеры запускаются автоматически.

### Команды фронтенда

- `npm run dev` - сборка в режиме наблюдения
- `npm run build` - production сборка
- `npm test` - тесты
- `npm run test:watch` - тесты в режиме наблюдения
- `npm run eslint` - проверка ESLint

## Структура проекта

Монорепозиторий с разделением на backend и frontend.

### Backend (Django)

- `personal_website/` - настройки проекта
- `accounts/` - управление пользователями
- `blog/` - блог (статьи, категории, серии, темы, комментарии)
- `gallery/` - галерея (альбомы, фотографии, теги)
- `main/` - главная страница
- `api/` - REST API (JWT аутентификация, эндпоинты)
- `backup/` - резервное копирование (management-команды)
- `templates/` - Django шаблоны для React интеграции

Рекомендуемые паттерны:

- Class-Based Views для представлений
- ModelForms для работы с формами
- Наследование шаблонов
- Пользовательские менеджеры для сложных запросов к базе данных
- Декомпозиция функций по модулям по назначению: `utils.py` - вспомогательные функции, которые вычисляют и подготавливают данные, но не выполняют операций; `services.py` - функции, выполняющие операции

### Frontend (React)

- `src/components/` - компоненты: Alert, Blog, Gallery, Main, Navbar, Card, Pagination, Spinner
- `src/hooks/` - кастомные хуки (useApiData, usePagination, usePhotoData, usePhotoNavigation, useToggle)
- `src/services/` - API сервисы (api.js, blogService.js, galleryService.js)
- `dist/` - production бандл

### Комментарии в коде

Правила относятся к обычным комментариям; обязательность docstrings публичных классов и функций не меняется.

- Комментарий оправдан, только когда добавляет неочевидное: причину нетривиального решения, внешнее ограничение, неявный контекст
- Не пересказывать код: условие if, имя маршрута, порядок строк говорят всё сами
- Не оставлять комментарии о прежнем или удаленном поведении: история изменений живет в git и CHANGELOG; удаляя код, удалять его комментарии целиком
- Перед коммитом вырезать комментарии, отвечающие на вопрос «что делает код», вместо «почему так»

## Тестирование

- Тесты backend - pytest с pytest-django: `poetry run pytest`
- Тесты фронтенда - Jest: `npm test`
- Unit-тесты бизнес-логики
- Интеграционные тесты представлений
- Проверка граничных случаев и обработки ошибок
- Писать тесты для нового функционала
- Покрывать все нетривиальные функции модуля: копирует файлы - проверять реальное копирование, есть флаги - проверять их работу
- Фабрики (factory_boy, model_bakery) и фикстуры для тестовых данных
- Тесты на базе django.test (TestCase, SimpleTestCase)
- Названия тестовых классов - TestClassName, не ClassNameTest
- Без patch/mock (unittest.mock): поведение проверяется на реальных операциях и чистых функциях; тест, который нельзя спроектировать без подмены функций, бесполезен и удаляется
- Без os.environ: конфигурация через override_settings (self.settings для динамических значений); тесты, которые нельзя переложить на override_settings, удаляются

### Тесты перед коммитом

- Перед коммитом изменений в исходном коде запускать тесты, даже если изменения кажутся незначительными
- Backend тесты: `poetry run pytest`
- Frontend тесты: `npm test`
- Изменения только в backend - достаточно pytest
- Изменения только во frontend - достаточно npm test
- Изменения в обеих частях или общая интеграция - оба набора тестов
- Не коммитить код, если хотя бы один набор тестов падает с ошибками

## Workflow разработки

- Не пушить изменения напрямую в main: ветка для изменений, мердж через Pull Request
- Формат коммитов: `<type>: <краткое описание>` на русском языке, type - fix, feat, refactor, docs, test и другие
- Без упоминаний AI-ассистентов и атрибутов Co-Authored-By

### Pre-commit

- Хуки автоматически проверяют код перед каждым коммитом: форматирование, линтинг, проверку типов
- Ручной запуск: `pre-commit run --all-files`
- Обновление хуков: `pre-commit autoupdate`

### Приоритеты

- Сохранять существующую архитектуру и подходы
- Не отменять ранее принятые архитектурные решения без согласования пользователя

### Скрипты деплоя

- Не запускать на локальной машине: scripts/deploy.sh, scripts/docker/deploy.sh, scripts/server/deploy.sh
- Скрипты переключают рабочую копию на main, останавливают стек (docker compose down) и удаляют неиспользуемые образы Docker всей машины (image prune)
- Выполняются на целевом сервере: CI/CD или вручную по SSH
- Локальная проверка - статическая: bash -n, shellcheck, разбор логики
- Полный прогон - на тестовом хосте

### Внешние правки файлов

- Правку, измененную извне (пользователем или линтером) и помеченную как намеренную, не откатывать и не восстанавливать измененное или удаленное содержимое
- При непонимании причины - уточнить у пользователя, а не возвращать измененное молча

### Исправление закоммиченных изменений

- Не сбрасывать ветку к main и не уничтожать промежуточные коммиты целиком
- Большинство изменений обычно корректны: отбрасывание ради «чистой истории» теряет правильную работу
- Вносить аккуратные точечные правки поверх существующих коммитов: коммит-исправление либо amend, если коммит еще не запушен
- Сброс к main допустим, только когда неверна вся совокупность изменений и перерабатывать нечего

## Линтинг и проверки

- Ruff: `poetry run ruff check . --fix`
- Mypy: `poetry run mypy .`
- ESLint: `npm run eslint`
- Markdown: `npx markdownlint-cli '**/*.md' --ignore-path .gitignore`
- Стиль кода поддерживают ruff, black, isort
- Без `# type: ignore`
- Сообщения об ошибках не игнорировать
- Код с ошибками не коммитить
- Явное преобразование типов, например `dict(obj)`

## Обновление CHANGELOG.md

- Следовать структуре файла: формат дат, стиль записей, порядок разделов
- Новые записи - в стиле существующих, без усложнения формулировок и лишних подробностей
- Описания емкие: что изменилось, без причинно-следственных объяснений и деталей реализации
- Без ссылок на задачи (номера вида #N)
- Подзаголовок с текущей датой в формате YYYY-MM-DD
- Получить diff с основной веткой: `git diff main > tmp/changelog.diff`
- Обновить CHANGELOG.md в текущем стиле
- Удалить временный diff: `rm tmp/changelog.diff`
- Проверить: `npx markdownlint CHANGELOG.md`

## Описание Pull Request

- Получить diff с основной веткой: `git diff main > tmp/changes.diff`
- По нему создать `pr_description.md` в формате Markdown
- Проверить markdownlint-cli и исправить замечания
- Удалить `tmp/changes.diff`

## Документация

- Техническая документация на русском языке
- Обновляется при изменении функциональности
- Понятные имена переменных и функций
- Комментарии сложной логики в коде
- Документировать только актуальное состояние: история изменений и причины решений живут в коммитах и CHANGELOG.md
- Глаголы в неопределенной форме, а не в повелительном наклонении («удалить», а не «удалите»)
- docs/ - связная проза для людей: полные предложения со сказуемыми, связный текст разделов, объяснения «почему» и «что из этого следует»; рубленый телеграфный стиль уместен только в скиллах (.agents/skills/), списках команд и CHANGELOG.md
- Без жирного шрифта и выделений
- Акценты - структурой и порядком пунктов

### Типографика

- Вместо длинного тире (U+2014) писать дефис "-"
- Вместо стрелки (U+2192) писать "->"
- Действует во всех текстовых файлах: документация, комментарии, docstrings, строки кода

## Безопасность

- Проверять права доступа к представлениям
- Использовать встроенную защиту CSRF Django
- Экранировать пользовательский ввод в шаблонах
- Не хранить конфиденциальные данные в коде
